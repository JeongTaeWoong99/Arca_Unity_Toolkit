# 스킬 동기화 (프로젝트 ↔ 전역 마스터)

작업 중 프로젝트에서 수정한 규칙을 전역 마스터에 반영하거나,
마스터의 최신 내용을 현재 프로젝트로 가져온다.

- 마스터 위치: `~/.claude/skills/unity-project-setup/templates/`
- 프로젝트 위치: `.claude/skills/` + `<스크립트 루트>/Common/` + 루트 `CLAUDE.md`

---

## ⚠️ 먼저 — 이 스킬이 막으려는 것

마스터의 스킬·코드는 **공동 소유다.** 여러 프로젝트에 심기고, 여러 사람이 각자의 프로젝트에서
고친다. 그래서 **양쪽이 각각 따로 바뀌어 있는 상태**가 정상적으로 발생한다.

**이 스킬은 그 상태를 자동으로 병합하지 않는다.** 한쪽을 덮으면 남의 개선이 조용히 사라지고,
사라진 줄도 모른다 — 되돌리기가 비싼 종류의 사고다.
자세한 배경은 마스터의 [`templates/skills/README.md`](../unity-project-setup/templates/skills/README.md).

---

## 절차

### 1. Diff 수집

세 갈래를 모두 본다.

| 대상 | 프로젝트 | 마스터 |
|------|----------|--------|
| 스킬 | `.claude/skills/` | `templates/skills/` |
| 범용 코드 | `<스크립트 루트>/Common/` | `templates/code/Common/` |
| 문서 골격 | 루트 `CLAUDE.md` | `templates/CLAUDE.md.template` |

- 스킬은 폴더 안에 있는 **모든 `.md`** 를 비교한다. `SKILL.md`뿐 아니라 **같은 폴더의 상세 문서**
  (예: `clean-code-style/스타일 상세.md`)도 대상이다 — `SKILL.md`만 보면 분리된 상세 문서를 통째로 놓친다.
- 범용 코드는 `.cs`와 **자산 폴더의 `<폴더명> 규칙.md`** 를 함께 본다.
  `.meta`·`.asset`은 비교 대상이 아니다(마스터에 두지 않는다).
- 한쪽에만 있는 파일도 차이로 본다.
- ⛔ **소유 표식 블록은 차이가 아니다.** `SKILL.md` 상단의 `> 🔗 **공동 소유** …` 3줄은
  **마스터에만 두는 주석**이다. 프로젝트 사본에는 없는 것이 정상이므로 diff에서 제외한다.
  프로젝트 저장소의 스킬은 협업자와 함께 쓰는 파일이라, 내 개인 툴킷 사정을 적으면 그 사람에게는
  뜻 모를 문구가 된다. **push 할 때 이 블록을 붙이고, pull 할 때 떼어 낸다.**
- **`> 최종 업데이트:` 줄만 다른 것도 차이로 치지 않는다** — 내용이 같으면 날짜는 뒤따라 맞춘다.
- `CLAUDE.md`는 placeholder·프로젝트 고유 내용을 차이로 치지 않는다.
- 차이가 없으면 "동기화 완료 상태"라고 보고하고 종료한다.

### 2. 변경 건별 분류 — 세 갈래다

| 분류 | 기준 | 처리 |
|------|------|------|
| **범용** | 어떤 유니티 프로젝트에도 적용 가능한 규칙·코드 (스타일, 설계 원칙, 커밋 규칙, 게임을 모르는 컴포넌트) | 마스터 반영 후보 → **사용자 확인 후** push |
| **프로젝트 특화** | 프로젝트 고유 경로·고유명사·서버 스펙·특정 에셋/씬 이름이 포함된 내용 | 프로젝트에만 유지 + **왜 특화인지 한 줄 기록**해 보고에 남긴다 |
| ⛔ **충돌** | 마스터와 사본이 **각각 따로** 바뀌었다 | **자동 병합 금지.** 아래 3-B |

**충돌 판정 근거** — 두 가지를 함께 본다.

- 양쪽 md 상단의 `> 최종 업데이트:` 날짜
- `git log`(마스터 저장소 / 프로젝트 저장소)에서 그 파일이 마지막으로 바뀐 시점

마스터가 사본보다 최신이면 **다른 프로젝트에서 먼저 반영된 변경**이다. push로 덮지 않는다.

> 📌 **프로젝트 특화 판정은 내용으로 한다.** 고유 경로(`GameDesign/Excel`)·기획 문서 이름·서버 스펙이
> 들어 있으면, 그것을 걷어냈을 때 **남는 게 껍데기인지**를 본다. 껍데기면 프로젝트 특화다.
> 실제로 `excel-table-creator`·`game-design-reference`가 그 이유로 마스터에 없다.

### 3-A. 범용 — 사용자 확인 후 적용

- 분류 결과를 표로 보여주고, **범용 후보만** 마스터 반영 여부를 확인받는다.
- ⚠️ **공동 소유 표식이 붙은 파일은 범용으로 분류돼도 건별로 개별 확인한다.**
  "전부 반영할까요?"로 묶지 않는다 — 남이 쓴 규칙의 의도를 지울 수 있다.
- 승인된 항목을 방향에 맞게 적용한다:
  - **push**: 프로젝트 → 마스터 (`templates/`의 해당 파일 갱신)
  - **pull**: 마스터 → 프로젝트 (마스터가 더 최신일 때; 프로젝트 특화 수정을 덮어쓰지 않게 주의)
- 새 스킬이 프로젝트에서 만들어졌고 범용이면, 마스터에 추가하고
  `templates/skills/README.md`의 "지금 있는 것" 표와
  `templates/CLAUDE.md.template`의 Skills 참조표에도 행을 추가한다.
  **원작이 누구인지도 함께 적는다.**
- 새 코드 자산이면 `templates/code/README.md`의 자산 목록에 행을 더한다.

### 3-B. ⛔ 충돌 — 줄 단위로 확인받는다

**어느 한쪽을 통째로 고르지 않는다.** 양쪽 diff를 나란히 보이고, **바뀐 덩어리마다**
어느 쪽을 남길지 물어 병합안을 만든 뒤 승인을 받는다.

```
[파일] templates/skills/common/task-writer/SKILL.md
  마스터 (2026-09-02, 다른 프로젝트에서 반영)   ↔   이 프로젝트 사본 (2026-09-05)
  ① 「담당 필드」 절     : 마스터에만 있음  → 남길까요 / 버릴까요
  ② 「완료 처리」 절     : 양쪽이 다름      → 마스터 / 사본 / 합침
```

- 판단이 서지 않으면 **그 파일은 건너뛰고 보고에 남긴다.** 억지로 합치지 않는다.
- 병합 결과는 **양쪽 모두**에 반영한다 — 한쪽만 고치면 다음 sync에서 또 충돌한다.

### 4. 날짜 갱신 및 마무리

- **수정된 모든 md 파일**(마스터·프로젝트 양쪽)의 상단 `> 최종 업데이트:` 라인을
  오늘 날짜(YYYY-MM-DD)로 갱신한다. 수정하지 않은 파일의 날짜는 건드리지 않는다.
- 적용 결과를 요약 보고한다: **마스터 반영 N건 / 프로젝트 유지 N건 / pull N건 / ⛔ 충돌 N건**.
  충돌은 해결됐는지 미해결인지를 나눠 적는다.
- **마스터 저장소 커밋은 하지 않는다.** 변경만 해 두고 사용자가 직접 커밋한다.
  (형식을 제안할 수는 있다: `docs: 스킬 동기화 - <요약>`)

---

## 규칙

- **사용자 확인 없이 마스터를 수정하지 않는다.**
- **충돌을 자동 병합하지 않는다.** 이 스킬의 존재 이유가 그것이다.
- 프로젝트 사본을 직접 고치는 것 자체는 **허용한다.** 막는 것은 되돌림을 건너뛰는 것뿐이다.
- 마스터로 올릴 때 **프로젝트 고유명사가 남아 있는지 마지막에 한 번 더 훑는다** —
  경로·클래스 이름·씬 이름·서버 스펙. 하나라도 남으면 다음 프로젝트가 존재하지 않는 것을 가리킨다.
